# Тренажёр юного разработчика — дизайн (очередь 1)

Дата: 2026-10-30. Первое занятие: **3 ноября 2026** (до него — установка и тестирование).

## Зачем

Удалённые занятия для подростков (13+) по работе с консолью, кодом и LLM-агентами. Сейчас каждый подключается к учебному серверу кто чем (PuTTY на Windows, Terminal на Mac) — это хаос, а на одном из занятий ученики удалили не те файлы и положили общий сервер.

Нужен единый учебный центр в браузере: у каждого ученика своя комната с агентами, свой изолированный контейнер с терминалом и бэклог индивидуальных заданий. Агенты задают ученику вопросы, ведут его и сами проверяют результат в его контейнере. Преподаватель видит всех сразу.

## Как выглядит занятие

1. Преподаватель заранее описывает урок в админке (тема, цели, что ученик должен уметь). Пример: «Bash: подключение по ssh, ls, cd, touch, rm, права файлов».
2. Агент-методист по описанию урока и профилю каждого ученика готовит **индивидуальный** набор заданий с критериями проверки. Преподаватель просматривает, правит, одобряет — только после этого задания попадают ученикам.
3. Ученики заходят каждый со своего компьютера под своим логином. Видят панель (как в DocOps), по центру — свою комнату: при входе в ней включается свет и появляются агенты.
4. Ученик берёт задание из бэклога и отправляет его агентам. Агенты задают вопросы («как подключаемся к серверу?»), ученик отвечает в чате и выполняет команды в терминале своего контейнера.
5. Агент (например, «Девопс») проверяет результат **сам в контейнере** (есть ли файл, какие права, удалена ли папка Tmp, есть ли Temp/test.py), видит историю команд. Не так — наводящий вопрос, без готового ответа. Так — «ОК», задание закрыто.
6. Преподаватель во вкладке «Офис» видит все комнаты: кто в сети, кто над чем работает, кто ждёт ответа.

Примеры заданий: «создай файл, внеси в него текст, посмотри права»; «найди папку Tmp, удали её, создай Temp и в ней test.py». С каждым уроком сложнее: дальше ученики пишут и запускают сервисы, работают с git/GitHub.

## Цели (очередь 1, к 3 ноября)

- Урок по bash проходит целиком: вход → индивидуальные задания → терминал → вопросы агентов → проверка в контейнере → «ОК».

- Преподаватель полностью управляет агентами, моделями, ключами и тем, что видят ученики.

## Анти-цели (провал, даже если «работает»)

- Действия ученика могут повлиять на сервер, на других учеников или на соседние проекты на VPS.
- Ученик видит ключи LLM или может менять агентов/модели.
- Агенты выдают готовые решения вместо того, чтобы вести ученика вопросами.
- Задание, не одобренное преподавателем, попадает ученику.
- Разные интерфейсы на разных ОС — всё должно работать одинаково в браузере.

## Роли

- **Преподаватель.** Создаёт группу, задаёт число учеников (2–5), заводит им логины/пароли, пишет заметку о каждом ученике (уровень, опыт). Описывает уроки, запускает подготовку заданий методистом, правит и одобряет задания. Настраивает провайдеров LLM, ключи, агентов (роль, промпт, правила, модель, лимиты), бюджет на ученика. Видит все комнаты. Может пересоздать контейнер любого ученика.
- **Ученик.** Только пользуется: видит свою комнату, свой бэклог, свой терминал, чат с агентами своей комнаты. Может пересоздать свой контейнер. Git/GitHub подключает сам (генерирует ssh-ключ в контейнере и добавляет в свой аккаунт GitHub — это часть обучения; ученикам 13+, что соответствует правилам GitHub).

## Офис и присутствие

- Офис группы содержит столько комнат, сколько учеников в группе (2–5), — задаётся преподавателем.
- **Свет в комнате горит и агенты появляются только когда ученик в сети** (авторизован и страница открыта). Не подключился — комната тёмная и пустая.
- Внутри комнаты — агенты, назначенные ученику, их состояния (думает / проверяет / ждёт ответа ученика / готово), как в офисе DocOps.
- Ученик видит свою комнату; преподаватель — все комнаты группы одновременно.
- **Что видит преподаватель:** у себя в панели — комнату каждого ученика; над чем работают агенты ученика; может прощёлкать каждого агента и посмотреть, кто над чем работает. **Ответы LLM — в отдельном окне по каждой комнате** (лента ответов агентов этой комнаты). Чат ученика и его терминал преподавателю не нужны (на занятии преподаватель показывает свой экран); писать в терминал/чат ученика преподаватель не может.

## Учебный план и задания

- Структура: учебный план → уроки (описание пишет преподаватель) → задания конкретного ученика (готовит методист).
- Задание содержит: формулировку для ученика, критерии проверки для агента (что проверить в контейнере), статус. Статусы минимум: черновик (ждёт одобрения) → в бэклоге → в работе → ждёт ответа ученика → выполнено.
- Индивидуальность с первого урока: методист опирается на заметку преподавателя об ученике.
- По каждому заданию копится история: вопросы и ответы, команды, попытки проверки, сколько раз «не так». Это материал для профиля ученика в очереди 2.

## Песочница ученика

- Отдельный Docker-контейнер на ученика, с жёсткими лимитами памяти, CPU и числа процессов, без доступа к Docker-сокету и к другим контейнерам. Выход в интернет нужен (git push в GitHub).
- Внутри: Linux с bash, coreutils, nano, python3, git, ssh-клиентом.
- Содержимое домашней папки сохраняется между занятиями до пересоздания.
- Кнопка «пересоздать с нуля» — у ученика (для себя) и у преподавателя (для любого).
- Терминал — в браузере, внутри панели, одинаковый на любой ОС. Рядом с ним — чат с агентами.
- Урок «подключись по ssh» сохраняет смысл: ученик сам набирает команду ssh с **учебными** логином и паролем (они не от сервера, а для урока) и попадает в свою песочницу. Агент спрашивает, как подключаемся, и проверяет.
- *Решение разработчика (не обсуждалось):* ssh набирается **в браузерном терминале**, а не на компьютере ученика: терминал открывается во «внешней» оболочке, ssh ведёт внутрь песочницы. Наружу в интернет ssh-вход для учеников не открываем. Проверяющий агент видит и то, что набрано во внешней оболочке.

## Агенты

- Берутся из модели агентов DocOps (карточка агента: роль, промпт, правила, модель, лимиты). Всё настраивает преподаватель.
- Нужны минимум две роли: **методист** (готовит задания по описанию урока и заметке об ученике) и **проверяющий** (например, «Девопс»: ведёт ученика вопросами и проверяет результат в контейнере).
- Проверяющий агент должен уметь сам выполнять в контейнере ученика проверочные команды и видеть историю команд ученика.
- Ученику агенты задают вопросы и дают наводки, но не готовые ответы.
- Ключи LLM — у преподавателя; расход считается по каждому ученику, у каждого свой потолок.
- **Провайдеры:** адаптеры шлюза DocOps берём как есть. Преподаватель подключит **OpenRouter** и **Hugging Face** и выберет модели. Для проверяющего агента нужна модель с надёжным tool calling — проверить вживую с VPS до занятия.
